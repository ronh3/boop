<interfaces>
Existing interfaces to evolve without creating a second room truth:
- `boop.runtime.startRoomObservation(roomId)` currently always increments the generation and marks Info seen.
- `boop.runtime.stampRoomItemsObservation()` currently reads persistent `gmcp.Room.Info.num` and returns a boolean.
- `boop.runtime.roomObservationSnapshot()` currently returns generation, roomId, Info/items flags, and refresh state.
- `boop.onRoomItemsList()` currently authenticates, updates targets, detects gold, ticks, and settles walk in one handler.
- `boop.onRoomInfo()` currently starts a new observation and cancels room-owned gold before comparing room IDs.

Canonical contract produced by this plan:
- `boop.runtime.startRoomObservation(roomId, opts)` is the only epoch-advance API. `opts.boundary` is exactly `room_change` or `fresh_start`; either boundary increments once, clears accepted items, invalidates older fences, and resets capped-refresh state. No same-room refresh calls it.
- `boop.requestRoomItemsOnce(reason)` is the only fence opener. Before any network side effect it appends `{ fenceId, generation, roomId, phase = "await_inv", valid = true }`, marks the epoch's one capped attempt, and arms its warning timer; it then calls `sendGMCP("Char.Items.Inv")` followed immediately by `sendGMCP("Char.Items.Room")`.
- Advancing the room epoch marks every older queued fence `valid = false` but does not delete or relabel it. Responses consume only the queue head in the sent request order: an `inv` List moves that head to `await_room`; the following `room` List consumes that head. Invalid heads drain with zero room effects before a newer head can become eligible.
- `boop.runtime.observeRoomItemsList(location, items)` deep-copies the event-time payload and returns `inventory`, `awaiting_inv`, `accepted`, `rejected`, `duplicate`, or `drained`. `accepted` is possible only for the current valid queue head after its inventory response and when the head's generation/roomId still equal the canonical epoch and normalized current Room.Info ID.
- The production validity rule is the distinguishable response sequence itself. Event/completion serials may support idempotency, but serials, timestamps, copied payloads, persistent `gmcp.Room.Info`, persistent `gmcp.Char.Items.List`, and test-only labels are never sufficient to authorize a room List.
- `boop.runtime.observeRoomInfo(roomId, opts)` accepts `opts.movedRooms` and `opts.previousRoom`; it preserves a same-room complete epoch and never binds a List. A same-room incomplete epoch may request its one missing fence but does not advance.
- `boop.runtime.roomObservationSnapshot()` returns deep copies of accepted items, fence queue/current phase, capped timeout/warning state, generation, roomId, and completeness. Mutating a snapshot cannot alter runtime state.
- `boop_events.lua` owns one local accepted-items transition applicator. Inventory Lists still rebuild inventory/wield state, but cannot touch room consumers. Targets, gold detection/advancement, tick reevaluation, and walker settlement consume only copied `transition.items` from `accepted`.
</interfaces>

<assumption_delta>
`changed`: Phase 03 research and Plans 03-01/03-05 assumed every Room.Info starts a new ordered Info→List generation and invalidates room-owned pickup. Live UAT disproved that assumption, and the prior gap-plan draft still lacked production evidence for binding a room-ID-less List. Locked D-09 says a room change invalidates acquisition, while D-16 says duplicate same-room callbacks are ignored; therefore normalized actual movement or D-23 fresh start—not any List or tokenless arrival—is the epoch boundary. The official IRE GMCP contract says Char.Items.Inv and Char.Items.Room each cause a location-distinguishable Char.Items.List response; the production adapter has one List handler, already separates inv from room, uses Add/Remove/Update for incremental inventory changes, and the repository has no competing Char.Items.Inv requester. This plan therefore uses the serialized TCP/GMCP request order as the fence, retains old request pairs as drain-only queue heads, and fails closed if the expected inv→room response order is absent, mismatched, or stranded. No unbound candidate is ever guessed current.
</assumption_delta>
