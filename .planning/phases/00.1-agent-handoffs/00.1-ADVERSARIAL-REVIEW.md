### M-02 — Approval tags carry no authenticity binding and no name-to-target check

- **Severity:** Medium
- **Location:** `AGENTS.md:143-159`; `AGENTS.md:104`.
- **Violated invariant:** `AGENTS.md:110` — "This is a role contract; Git author
  names do not authenticate a human."
- **Problem:** The tag is now the single terminal artifact of merge
  authorization: `AGENTS.md:104` says "The tag, not a later STATE or UAT entry,
  is final authorization evidence." Three properties it is relied on for are not
  established:
  1. **Name/target binding.** `phase-<phase>-approved-<12-char-commit-sha>`
     embeds a SHA prefix, but nothing verifies the tag actually targets the
     commit that prefix names. A tag named for SHA X pointing at commit Y
     satisfies every check in the repository.
  2. **Authenticity.** `AGENTS.md:110` already concedes Git identity cannot
     authenticate a human — and `AGENTS.md:144-146` makes **Codex** the actor
     that creates the tag. An unsigned annotated tag created by the same agent
     the contract distrusts elsewhere carries no more authority than a commit
     whose author line says "Ron". Moving authorization "outside the commit
     tree" buys ordering and immutability against rebase; it does not buy
     authenticity.
  3. **Immutability.** `AGENTS.md:150-151` asserts tags are "immutable evidence
     once pushed," but Git tags are force-movable by default; no server-side tag
     protection ruleset is evidenced in the repository, and nothing in-tree can
     detect a moved tag.

  Separately, because the tag name is a deterministic function of the SHA, a
  superseded authorization stays permanently valid: `AGENTS.md:155-157` requires
  a *new* tag after branch mutation but never invalidates the old one, so
  re-merging a previously authorized-but-superseded SHA passes every stated
  check.
- **Failure scenario:** After a correction round, an agent finds the earlier
  `phase-01-approved-<old-sha>` tag, confirms it peels to a commit, confirms the
  name matches, and fast-forwards `main` to the pre-correction commit. Every
  documented pre-merge verification in `AGENTS.md:152-157` compares the tag to
  itself and passes.
- **Smallest correction:** Add a guard that, for every `phase-*-approved-*` ref,
  asserts the peeled target SHA begins with the 12-char prefix in the tag name;
  require GPG/SSH-signed tags or a GitHub tag-protection ruleset for authenticity
  and immutability, and state in `AGENTS.md` that a superseded approval tag is
  void for merge once a newer tag exists for the same phase.

### M-03 — Ready handoffs have no completion or expiry semantics and are indefinitely replayable

- **Severity:** Medium
- **Location:** `AGENTS.md:166-219`; `.planning/CLAUDE-NEXT.md:3` and its
  `# Constraints` / `# Completion Boundary` sections.
- **Violated invariant:** `AGENTS.md:184-185` — "Updating a handoff does not
  execute it; the human remains the trigger."
- **Problem:** Nothing defines what a handoff's state becomes after it is
  executed. `CLAUDE-NEXT.md` will still read `status: ready` with
  `review_target_sha: a9a8e72` after this review is recorded, because:
  - its `# Completion Boundary` does not instruct the agent to reset it, and
  - its `# Constraints` explicitly forbid Claude from editing "either NEXT
    mailbox" — correctly, per `AGENTS.md:183-184`.

  So the assigned agent is structurally unable to retire its own handoff, and no
  rule obliges the assigner to. The pre-execution checks at `AGENTS.md:209-215`
  detect a *stale base* (`task_base_sha` not an ancestor, unexpected commits in
  the range) but not a *completed task*: after this review commit, `a9a8e72`
  remains an ancestor and the intervening commits are still "planning
  coordination," so a replay passes every check.
- **Failure scenario:** The human says "run the current handoff" a week later,

  cannot be removed.
- **Smallest correction:** Add a terminal state to the schema
  (`status: idle | ready | completed`) plus a rule at `AGENTS.md:209-219` that an
  agent must stop if its handoff's `review_target_sha` is already cited by a
  recorded entry in the phase's review artifact; or require the assigner to

## New defects introduced by the correction

### N-01 — The closure-tail baseline is derived from forgeable, order-sensitive free text

- **Severity:** High
- **Location:** `tools/check_merge_authorization.py:23-43` (`reviewed_targets`),
  consumed at `:50-53`.
- **Violated invariant:** `AGENTS.md:22-34` — independent adversarial review
  precedes closure; `AGENTS.md:73-79` — Codex may append to the review artifact
  but "may not mark any finding finally accepted, resolved, or closed."
- **Problem:** `closure_tail_errors` decides which commits count as "after the
  review" by running three regexes over the adversarial-review artifact and
  taking `targets[-1]`. Two properties follow:
  1. **The anchor is writable by the constrained actor.** The artifact is
     append-only, but Codex is authorized to append to it. Any appended line
     matching `**Reviewed SHA:** \`<40 hex>\``, `**Reviewed target SHA:** …`, or
     `Reviewed target SHA: …` at the start of a line becomes the new review
     baseline. No authorship, section, or role check exists — `AGENTS.md:81-82`
     already concedes that prefix preservation cannot authenticate the author of
     a new entry, and this check now depends on exactly that.
  2. **Selection is by pattern group, not document order.** The three patterns
     are applied in sequence and their results concatenated, so with mixed
     heading forms `targets[-1]` is the last match of the last non-empty
     *pattern*, not the newest entry in the file. Reproduced with a synthetic
     artifact containing forms 1, 2, 1 in that order: the middle (older) SHA is
     selected. This direction is fail-safe on its own — an older baseline widens
     the tail — but it means the "latest reviewed target" is not actually what
     the function computes.
- **Failure scenario:** Reproduced end to end in a scratch repository. A commit
  adding `src/scripts/boop/unreviewed.lua` after the recorded review is
  correctly rejected: `unreviewed post-review change is not permitted in closure
  tail: src/scripts/boop/unreviewed.lua`. One further commit appending the
  single line `Reviewed target SHA: <HEAD>` to the review artifact — a permitted
  append to a permitted path — moves the baseline past the offending commit, and
  `closure_tail_errors` then returns no errors. The unreviewed source change is
  retroactively legitimized, and the check that `AGENTS.md:152` designates as
  the pre-merge safeguard reports clean. No forgery of Git identity, no tag
  manipulation, and no gate bypass is required; the appended line need not even
  be deliberate, since any Codex correction entry quoting a SHA under one of
  these headings has the same effect.
- **Smallest correction:** Anchor the baseline to something Codex cannot write —
  for example, require the reviewed target to be read from the
  Claude-owned `independent_review` field in `STATE.md` (whose writer the role
  contract already names) and require it to agree with the review artifact,
  rather than trusting the artifact alone. Independently, collect all three
  patterns in a single alternation so `targets[-1]` is genuinely the last
  occurrence in document order.

### N-02 — "Newest valid approval tag" falls back to lexicographic SHA-prefix order

- **Severity:** Low
- **Location:** `tools/check_merge_authorization.py:130-136`.
- **Problem:** `valid` holds `(taggerdate_unix, name)` tuples and the winner is
  `max(valid)`. When two approval tags for the same phase share a taggerdate —
  routine when both are created by a script, and trivially arranged since
  `GIT_COMMITTER_DATE` is writer-controlled — the tie is broken by comparing tag
  *names*, i.e. by the lexicographic order of an arbitrary hex SHA prefix. The
  selected tag is then unrelated to recency. `AGENTS.md:157-159` calls this "the
  newest valid approval tag"; the implementation does not compute that.
- **Failure scenario:** Reproduced across six trials with two tags stamped at an
  identical `taggerdate:unix`. In one trial the stale tag's SHA prefix sorted
  higher, was selected as "latest", and authorization of the genuinely newer
  candidate failed with `peeled target does not equal authorized candidate` and
  `annotation must record the exact full target SHA`. The failure direction is
  fail-closed — a legitimate merge is blocked, never an illegitimate one
  admitted — so the impact is availability and operator confusion, not a bypass.
- **Smallest correction:** Break the tie deterministically on something ordered,
  such as preferring the tag whose peeled commit is a descendant of the other's,
  or reject outright when two valid tags for one phase share a taggerdate.

### N-03 — The bootstrap staged exception is bounded by content, not to one delivery

- **Severity:** Low
- **Location:** `tools/workflow_guard.py:222-245`; `AGENTS.md:244-247`.
- **Problem:** `AGENTS.md:244-246` says the staged gate "permits that one
  delivery boundary only when the staged change is exactly
  `.planning/CODEX-NEXT.md`". The implementation enforces the content clause but
  not the count: the predicate depends on the staged path set and on
  `merge-base(HEAD, origin/main) == origin/main == task_base_sha`, all of which
  remain true after the first delivery commit lands.
- **Failure scenario:** Reproduced. On a branch forked from the `origin/main`
  tip with STATE still naming the prior phase, a first `CODEX-NEXT.md`-only
  staged change is permitted (correct, per H-02), and after committing it a
  second `CODEX-NEXT.md`-only staged change is permitted as well. An indefinite
  run of mailbox-only commits can precede the CONTEXT/STATE update that
  `AGENTS.md:246-247` says ends the exception. Consequences are minor because
  only the mailbox can change, but the documented "one delivery boundary" is not
  what is enforced.
- **Smallest correction:** Additionally require `HEAD == origin/main` (the
  branch has no commits of its own yet), which admits exactly the first delivery
  commit; or state in `AGENTS.md:244-247` that the bound is on staged content
  rather than on commit count.

### N-04 — `review_target_sha` is never resolved or bounded to the repository

- **Severity:** Low
- **Location:** `tools/workflow_guard.py:104-108`.
- **Problem:** `task_base_sha` is checked with `rev-parse --verify` and
  `merge-base --is-ancestor` (`:96-103`), but `review_target_sha` is only
  matched against `[0-9a-f]{40}`. `AGENTS.md:230-232` describes the gate as

- **Failure scenario:** A handoff is assigned with a mistyped or stale 40-hex
  review target. Every gate passes, and the error surfaces only when the
  reviewer manually resolves the SHA — or does not, and reviews the wrong range.
- **Smallest correction:** Apply the same `rev-parse --verify` and ancestry
  check to a non-null `review_target_sha`.

### N-05 — `AGENTS.md` list-continuation indentation regression
